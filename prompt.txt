# 2. CORE ARCHITECTURAL REQUIREMENTS

Implement two major architectural environments.

## A. IN-STORE ARCHITECTURE

This environment manages physical retail operations.

Develop the following components.

### A1. Transaction Manager (TM)

The Transaction Manager is the central processing component of each retail installation.

Responsibilities:

1. Coordinate transactions across all connected client devices.
2. Manage communication between POS terminals, kiosks, OMS and peripherals.
3. Maintain local transaction storage and caching.
4. Process transaction requests.
5. Maintain transaction integrity.
6. Record transaction events.
7. Synchronize transactions with the cloud.
8. Handle interrupted network connections.
9. Retry failed synchronization operations.
10. Prevent duplicate transaction processing.
11. Receive and distribute software updates.
12. Enforce device licensing and authorization.
13. Monitor the operational health of connected clients.
14. Maintain transaction audit trails.

The Transaction Manager must remain operational during temporary internet outages.

Implement a reliable local-first transaction processing mechanism.

Transactions must be safely queued and synchronized when connectivity returns.

Use unique transaction identifiers, idempotency keys and synchronization checkpoints.

### A2. Client Manager

Develop a standalone Client Manager executable for each supported device.

Supported client types:

- POS terminals.
- Self-service kiosks.
- Digital menu displays (DMD).
- Order Management Systems (OMS).

Responsibilities:

1. Launch the appropriate client interface.
2. Communicate with the local Transaction Manager.
3. Receive configuration updates.
4. Report client health.
5. Receive authorized software updates.
6. Handle disconnections gracefully.
7. Maintain device identity and authorization.

Each Client Manager must operate independently while receiving centralized configuration and software updates.

### A3. Client User Interfaces

Create separate user experiences for:

**POS Interface**
- Product selection.
- Product search.
- Barcode scanning.
- Shopping cart.
- Order processing.
- Discounts.
- Tax calculations.
- Payment initiation.
- Receipt printing.
- Transaction history.
- Returns and refunds subject to authorization.

**Kiosk Interface**
- Customer self-service.
- Product browsing.
- Menu selection.
- Order placement.
- Order confirmation.
- Payment initiation.
- Receipt or order-ticket generation.

**Digital Menu Display**
- Dynamic product presentation.
- Pricing.
- Promotional banners.
- Product availability.
- Images and multimedia.
- Centralized content updates.

**Order Management System**
- Order reception.
- Order status.
- Order preparation.
- Order assignment.
- Order completion.
- Order cancellation.
- Kitchen or service workflow.

Where practical, kiosk and DMD interfaces should run independently from their Client Manager process, following the reference architecture's separate NEXTEP.UX process concept.

POS and OMS interfaces may run within their Client Manager process.

### A4. Peripheral Integration

Develop an extensible peripheral integration framework.

Provide adapter interfaces for:

1. Credit card terminals.
2. Cash and change machines.
3. Electronic weighing scales.
4. Magnetic stripe readers.
5. Barcode scanners.
6. Receipt and document printers.
7. KASA sensors.
8. Biometric devices.
9. Customer pagers.
10. Reservation management devices.

Support appropriate hardware communication mechanisms, including USB, serial ports, network protocols and vendor SDKs.

Do not assume that all hardware manufacturers use the same protocol.

Create independent adapters, device discovery, connection monitoring, error handling and integration testing.

Hardware integration must be extensible without modifying the core transaction engine.

### A5. Transaction Manager Server Integrations

Create integration interfaces for:

- Third-party POS platforms.
- Loyalty and rewards programmes.
- Third-party payment gateways.
- Electronic lockers.
- Reservations systems.
- Lodging and hospitality management systems.

Use REST APIs, webhooks, message queues or vendor-specific SDKs as appropriate.

Provide configuration-driven integration settings.

### A6. Transactional Data and Software Updates

The reference architecture specifies XML-based transactional data.

Preserve XML support for transactional records and exchange formats.

Implement:

- Local transaction logging.
- XML serialization and deserialization.
- Schema validation.
- Secure cloud synchronization.
- Transaction reconciliation.
- Failed synchronization recovery.
- Configuration distribution.
- Software update distribution.
- Update verification.
- Version tracking.
- Rollback mechanisms.

JSON may additionally be used for APIs and internal service communication.

Do not silently discard failed transactions.

Develop the cloud environment as a collection of independent, secure and maintainable services.

The cloud architecture must separate non-payment business information from sensitive payment processing.

The portal must provide:

- Organization management.
- Store/location management.
- Device management.
- Transaction monitoring.
- Operational dashboards.
- Configuration management.
- Software version monitoring.
- Reporting access.

- Store Administrator.
- Store Manager.
- Supervisor.
- Cashier.
- Reporting Officer.
- Technical Support.

Permissions must be enforced on the server, not merely hidden in the user interface.

## B2. RetailEase Scheduler

Develop a centralized scheduling service.

Responsibilities:

1. Schedule data synchronization.
2. Distribute configuration metadata.
3. Schedule software updates.
4. Maintain scheduled operational jobs.
5. Monitor task execution.
6. Retry failed jobs.
7. Maintain execution history.
8. Notify administrators about critical failures.

Use reliable background processing with persistent job status.

## B3. Licensing Services

Create a dedicated licensing subsystem.

The License Database must maintain:

- Customer licensing records.
- Subscription plans.
- Authorized stores.
- Authorized devices.
- Device registration.
- Software versions.
- License activation.
- License expiry.
- Renewal history.
- License restrictions.
- Activation and revocation history.

The licensing service must determine which software versions and devices are authorized.

Implement signed license credentials, server-side validation, controlled offline grace periods and secure device registration.

Never rely exclusively on client-side licensing checks.

## B4. Customer Databases

Follow the reference architecture's dedicated customer database approach.

Each customer must have an isolated database or an explicitly approved equivalent isolation boundary.

Each customer database should contain:

**Transactional Information**
- Orders.
- Order items.
- Transaction references.
- Discounts.
- Taxes.
- Refund records.
- Store operations.
- Inventory movements.

**Configuration Information**
- Products.
- Categories.
- Pricing.
- Menus.
- Promotions.
- Store settings.
- Device settings.
- System configuration.
- Printing rules.
- Theme metadata.

Maintain customer-specific configuration files and metadata.

Preserve support for system.xml and print-rules.xml as configuration formats where required.

Implement database provisioning, migration, backup, recovery and isolation testing.

## B5. SQL Reporting Services

Implement a comprehensive reporting subsystem.

Support SQL-based reporting and RDL report definitions.

Reports should include:

- Daily sales.
- Weekly sales.
- Monthly sales.
- Product performance.
- Store performance.
- Transaction summaries.
- Order status.
- Inventory movements.
- Discounts.
- Refunds.
- Tax summaries.
- Device activity.

Provide filtering by customer, organization, location, terminal and reporting period.

Reports must be accessible through the RetailEase customer portal.

Do not expose one customer's reporting data to another customer.

## B6. Software and Media Management

Develop a centralized software and media repository.

It must manage:

- Software packages.
- Application versions.
- Release channels.
- Patches.
- Configuration files.
- Branding assets.
- Themes.
- Product images.
- Promotional media.

Every software package must have:

- Release information.

- Rollback information.

The Transaction Manager must retrieve authorized updates and distribute them to appropriate client devices.

# 4. PAYMENT SECURITY ARCHITECTURE

Treat the Azure Non-PCI environment as a strictly separated environment.

Do not store raw card numbers, CVV values, PINs or other prohibited sensitive authentication data in the non-PCI databases.

Payment operations must be handled through properly scoped, certified payment providers and terminals.

RetailEase should store only the necessary payment references, transaction status, approved amounts and permitted reconciliation metadata.

Payment integration must undergo an independent PCI DSS scope and compliance assessment.

Never claim PCI compliance merely because payment data is excluded from a particular database.

# 11. TESTING AND ACCEPTANCE CRITERIA

Do not declare a module complete merely because it compiles.

Each module must pass its relevant automated tests.

Mandatory acceptance conditions:

1. A store can process supported transactions locally.
2. Transactions survive temporary internet disconnection.
3. Transactions synchronize after reconnection.
4. Duplicate transaction submissions do not create duplicate records.
5. Multiple client devices can communicate with the Transaction Manager.
6. Each Client Manager can identify and launch its assigned UI.
7. Unauthorized devices cannot access licensed services.
8. Configuration updates reach authorized devices.
9. Software updates are verified before installation.
10. Customer databases remain isolated.
11. Portal users cannot access unauthorized stores.
12. Reports reflect reconciled transactional information.
13. Peripheral failures do not corrupt transaction records.
14. Failed background jobs can be diagnosed and retried.
15. Backups can be restored and verified.
16. Sensitive payment authentication data is not stored in the non-PCI environment.
17. The system maintains auditable records of critical operations.

Provide evidence for every acceptance criterion.
